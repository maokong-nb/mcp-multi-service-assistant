# 评测报告

## 评测设计

- **评测集**：`dataset.json`，24 题，覆盖 5 类场景——单服务调用（datetime / weather / notes）、多服务串联（chained）、多轮记忆（multi_turn）、异常输入（robust）。
- **指标**：工具选择准确率（期望工具是否为实际调用子集）、答案关键词命中率、平均响应时延、单次调用成本（按 token 用量 × 刊例价估算）。
- **运行**：`python eval/run_eval.py`，结果 JSON 存入 `eval/results/`。

## 第一轮：mock 链路验证（2026-11-27）

目的：在无 API key 的条件下验证 MCP 连接、工具调度、记忆、日志全链路。mock 用规则路由代替 LLM，**结果不代表真实模型表现**。

| 指标 | 结果 |
|---|---|
| 工具选择准确率 | 23/24 = 95.8% |
| 答案命中率 | 22/24 = 91.7% |
| 平均时延 | 1.97 s（含真实天气 API 请求） |

### 发现的问题与修复

**问题**：第 23 题「查一下火星市的天气」中，mock 的城市提取规则把「市的」当成城市名发给了地理编码 API（日志：`GET /v1/search?name=市的`），属于无意义的错误请求；该题能过只是因为恰好返回了"未找到"。

**定位**：`host/llm.py` mock 路由的城市提取用 `text.split("天气")[0][-2:]` 截取，未剥离「的」「市」和动作词。

**修复**：改为「常用城市表优先 + 正则提取 + 动作词剥离」的 `_extract_city()`。

**复测**（2026-11-27 第二轮）：错误请求消失，24 题中 22 题双通过；工具准确率 95.8%、答案命中率 91.7%、平均时延 1.73 s。剩余 2 题失败均为 mock 自身能力边界，不影响真实模型：

- 第 5 题（时区换算）：mock 没有 `convert_timezone` 的路由规则；
- 第 21 题（多轮记忆回忆）：mock 不会检索会话记忆作答。

## 第二轮：真实模型评测

待配置 `LLM_API_KEY` 后运行，结果追加到本节。重点观察：

1. 串联题（16-19）中模型能否把前一个工具的结果组织进 `create_note` 的正文；
2. 多轮题（21-22）中模型能否利用会话记忆回答追问；
3. 异常题（23-24）中模型能否如实转告工具报错而非编造。
