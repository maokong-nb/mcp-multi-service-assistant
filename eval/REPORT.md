# 评测报告

## 评测设计

- **评测集**：`dataset.json`，24 题，覆盖 5 类场景——单服务调用（datetime / weather / notes）、多服务串联（chained）、多轮记忆（multi_turn）、异常输入（robust）。
- **指标**：工具选择准确率（期望工具是否为实际调用子集）、答案命中率（同义判分组，空白与 ℃/°C 归一化）、平均响应时延、单次调用成本（按 token 用量 × DeepSeek 刊例价折算，仅作横向参考）。
- **运行**：`python eval/run_eval.py`，每轮结果 JSON 存入 `eval/results/`。
- **评测模型**：k2d8-preview（OpenAI 兼容网关）。mock 模式仅用于无 key 时的链路验证。

## 定稿结果（2026-11-27 第八轮）

| 指标 | 结果 |
|---|---|
| 工具选择准确率 | 24/24 = 100% |
| 答案命中率 | 23/24 = 95.8% |
| 双项通过 | 23/24 = 95.8% |
| 平均时延 | 16.5 s（含天气 API 真实请求；时延主要来自生成模型） |
| 单题平均成本 | ≈ ¥0.0077（刊例折算；单轮全量约 8 万 token） |

唯一未双通过项：第 9 题（上海天气），Open-Meteo 接口瞬时错误，**模型如实转告"暂时无法获取、建议重试"而非编造天气**——属于期望的错误处理行为，非系统缺陷。

更早轮次还观察到：简单日期差（第 3 题）模型偶发心算绕过工具（答案正确但过程不可审计），已通过系统提示强化工具纪律，定稿轮未复发，留作长期观察项。

## 迭代记录：七轮评测发现的问题与修复

| 轮次 | 工具准确率 | 答案命中率 | 关键发现 → 修复 |
|---|---|---|---|
| mock R1 | 95.8% | 91.7% | mock 城市提取把「市的」发给地理编码 API（无效请求）→ 重写 `_extract_city` |
| mock R2 | 95.8% | 91.7% | 修复生效，剩余失败为 mock 能力边界，转真实模型 |
| LLM R1 | 95.8% | 62.5% | **判分方法缺陷**：8 题模型答案正确但因表述不同被关键词误判 → 升级为同义判分组 + 动态日期模板 |
| LLM R2 | 100% | 91.7% | **真实模型缺陷**：多轮题无视会话记忆谎称"没查到"（记忆就在历史里）→ system prompt 增加"先回看历史再作答"规则 |
| LLM R3 | 95.8% | 91.7% | **真实模型缺陷**：心算时区换算绕过工具（答案对、不可审计）→ prompt 强化工具纪律 |
| LLM R4 | 100% | 91.7% | 判分空白符问题（"2026 年 12 月 27 日"）→ 空白不敏感匹配 |
| LLM R5 | 100% | 95.8% | 同义词长尾（"已记好""未查到"）→ 判分组统一收敛 |
| LLM R6 | 100% | 95.8% | 判分全半角问题（℃ vs °C）→ 归一化 |
| LLM R7 | 95.8% | 100% | 第 3 题心算绕过工具（答案对、不可审计）→ 记录为观察项 |
| LLM R8 | **100%** | **95.8%** | 定稿。唯一失败为天气 API 瞬时错误，模型如实报错（期望行为） |

## 结论与边界

1. **工具调度可靠**：天气、笔记、时间三类服务的选择与串联（查天气→记笔记等）在 24 题上稳定，多轮记忆经 prompt 修正后可正常回看。
2. **评测本身需要被评测**：前半程的主要产出是发现判分口径问题（关键词误伤、空白符、全半角），修正判分后才暴露出两个真实的模型行为缺陷（无视记忆、心算绕工具）。
3. **边界**：结果基于单模型单次运行，存在抽样方差（各轮工具准确率 95.8%–100%）；时延与成本随所选模型变化；评测集 24 题规模有限，结论限于本项目覆盖的需求形态。
